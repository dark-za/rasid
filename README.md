# راصد — نظام متابعة الحضور والانصراف

نظام لعرض سجلات أجهزة البصمة SmartPSS وإدارة سجل الموظفين والورديات وإسنادات الموظفين المؤرخة للفروع والورديات. يوضح هذا الملف واجهات الإصدار الموجودة في الباكند؛ إعدادات التشغيل والتعافي موضحة في [دليل التشغيل](docs/OPERATIONS.md).

## المكوّنات

| المكوّن | التقنية | الوصف |
|---|---|---|
| `backend/` | FastAPI + SQLAlchemy | واجهة برمجية للحضور والورديات وإسناد الفروع |
| `frontend/` | React 18 + Vite | واجهة عرض (تُبنى إلى `frontend/dist`) |
| قاعدة راصد | SQLite | ملف محلي دائم `backend/data/rasid.sqlite3`؛ ينشئ التطبيق الجداول تلقائياً |
| قاعدة البصمة الخارجية | MySQL / SmartPSS | جدول `AttendanceRecordInfo` — **قراءة فقط**؛ لا تعديل على المصدر |

## المتطلبات

- Python 3.10+ (يُستخدم 3.12 محلياً و3.10 في صورة Docker)
- Node.js 18+
- اتصال قراءة إلى قاعدة SmartPSS الخارجية

### الاتصال بخادم قاعدة البيانات

قاعدة راصد محلية داخل ملف SQLite، ولا تحتاج خادم قاعدة بيانات أو حسابات أو تشفير كلمات مرور لها. بيانات الورديات والموظفين والتكليفات تحفظ في الملف تلقائياً. قاعدة SmartPSS منفصلة وتُستخدم للقراءة فقط؛ أدخل عنوانها وبيانات الدخول مرة واحدة من صفحة المشرف. بياناتها تحفظ في ملف إعدادات محلي بسيط `.db-runtime.env` أو في مجلد البيانات الدائم عند استخدام Docker.

## الإعداد الأول

```bash
# انسخ ملف الإعدادات في الجذر وضع بيانات دخول المشرف
cp .env.example .env

# أنشئ سر جلسات المشرف مرة واحدة
python -c "import secrets;print(secrets.token_urlsafe(32))"   # RASID_SESSION_SECRET

# ثبّت متطلبات backend؛ ملف SQLite والجداول يُنشآن تلقائياً عند بدء التشغيل
cd backend
python -m pip install -r requirements.txt
cd ..
```

## التشغيل المحلي

```bash
# الباكند
cd backend
python -m venv venv && venv/bin/pip install -r requirements.txt
venv/bin/uvicorn main:app --host 127.0.0.1 --port 8000

# الواجهة (تطوير — تُحوّل طلبات /api إلى الباكند على 8000)
cd frontend
npm install
npm run dev        # http://localhost:3005
```

## التشغيل بـ Docker

```bash
docker compose up --build -d      # الواجهة+الباكند
# الواجهة:  http://localhost:3005  (nginx يقدّم dist ويرسل /api إلى الباكند داخلياً)
```

- `docker compose` يقرأ `.env` من الجذر تلقائياً. قاعدة SQLite وملف اتصال البصمة محفوظان في حجم Docker دائم `rasid-data`.
- الباكند **بلا منفذ على المضيف** في وضع compose؛ يتصل بقاعدة SmartPSS الخارجية حسب بيانات `.env` أو صفحة المشرف.
- اسمح بالوصول إلى المنفذ 3005 من شبكة الشركة/VPN فقط؛ لا تنشر بيانات لوحة القراءة العامة إلى الإنترنت أو نفق عام. استخدم TLS داخل الشبكة عند الحاجة لحماية النقل.
- يحد Nginx تسجيل الدخول إلى 5 محاولات/دقيقة لكل عنوان IP، وبقية طلبات `/api/` إلى 10 طلبات/ثانية مع دفعة 30؛ يرد `429` عند التجاوز. إذا كان أمامه proxy، اضبط عناوين proxy الموثوقة قبل الاعتماد على عنوان العميل في التحديد.

## واجهة API

**تنبيه وصول:** فتح القراءة بلا تسجيل دخول يعني أن أسماء الموظفين وأرقامهم وحركات الحضور والتأخير والفروع يمكن لأي جهاز يصل إلى الموقع وواجهات API قراءتها. شغّل الموقع داخل شبكة الشركة أو VPN فقط، وقيّد المنفذ `3005` بجدار حماية لأجهزة/شبكات الشركة. لا تنشره على الإنترنت العام أو عبر نفق عام؛ TLS وحده لا يجعل بيانات العرض العامة خاصة.

بعد دخول المشرف، تتيح صفحة الإدارة إعداد اتصال SmartPSS واختباره وحفظه. تُحفظ الإعدادات في ملف محلي دائم، وتبقى كلمة المرور مخفية في الاستجابة. زر «جلب الموظفين من قاعدة البصمة» يستورد أرقام الموظفين وأسماءهم إلى SQLite؛ الورديات والإسنادات تدار وتُحفظ محلياً.

تسجيل الدخول يتم عبر `POST /api/auth/login` باسم المستخدم الافتراضي `admin` وكلمة مرور تضبطها في البيئة عبر `RASID_LOGIN_PASSWORD`. يعيد الخادم رمز جلسة صالحاً 8 ساعات؛ تحفظه الواجهة في الذاكرة فقط، ولا تحفظ كلمة المرور أو الرمز في التخزين المحلي للمتصفح، لذا يتطلب تحديث الصفحة تسجيل الدخول مجدداً. زر تسجيل الخروج يمسح الرمز من الصفحة؛ ويمكن إبطال كل الرموز فوراً بتغيير `RASID_SESSION_SECRET`. مسارات القراءة `GET` الخاصة بالحضور والتقارير والموظفين والورديات والسجلات عامة، ومسارات التعديل `POST` و`PUT` و`DELETE` تتطلب رمز المشرف؛ غياب الرمز أو خطؤه في التعديل = `401`. كلمة المرور وسر توقيع الجلسات مطلوبان، وإلا يعيد تسجيل الدخول `503`.

المسارات التالية هي واجهة الباكند المنفذة حالياً في `backend/main.py`. مسارات الصحة وتسجيل الدخول وجميع عمليات `GET` للقراءة عامة؛ أما عمليات التعديل فتتطلب مصادقة المشرف. في التشغيل المباشر يمكن الوصول إلى الباكند على المنفذ الذي شُغّل عليه (8000 في المثال)؛ في Compose لا يُنشر منفذ الباكند، وNginx يمرر `/api/` فقط، لذا يبقى `/` لواجهة الويب ولا تمرر مسارات الصحة إلى الباكند افتراضياً.

| المسار | الوصف |
|---|---|
| `POST /api/auth/login` | تسجيل دخول المشرف وإصدار رمز جلسة مؤقت |
| `GET /api/admin/database` | إعدادات اتصال قاعدة البصمة فقط؛ لا يعيد كلمة المرور |
| `POST /api/admin/database/test` | اختبار اتصال قاعدة البصمة فقط |
| `PUT /api/admin/database` | حفظ وتطبيق اتصال قاعدة البصمة بعد نجاح الاختبار؛ للمشرف فقط |
| `GET /` | معلومات النظام والوقت؛ لا يختبر اتصال قواعد البيانات (بلا مصادقة) |
| `GET /health/live` | فحص حياة العملية (بلا مصادقة) |
| `GET /health/ready` | فحص جاهزية قاعدة SQLite ومصدر البصمة (بلا مصادقة) |
| `GET /api/attendance/today` | بصمات اليوم: السجلات بعد فلترة التبصيم المتكرر + قائمة المتأخرين |
| `GET /api/attendance?date=YYYY-MM-DD&employee_id=16` | بصمات يوم محدد أو موظف؛ الافتراضي اليوم، والبحث محدود بآخر 90 يوماً |
| `GET /api/reports/late?from=YYYY-MM-DD&to=YYYY-MM-DD` | تقرير التأخير حسب الموظف والورديات المعيّنة؛ حتى 31 يوماً ضمن آخر 90 يوماً |
| `GET /api/shifts` | قائمة الورديات المحفوظة؛ تتضمن السماح وطريقة احتساب التأخير واللون وحالة التفعيل |
| `POST /api/shifts`, `PUT /api/shifts/{id}`, `DELETE /api/shifts/{id}` | إنشاء/تعديل/حذف وردية. النهاية الأسبق من البداية تعني نهاية اليوم التالي؛ تساويهما مرفوض. لا يمكن حذف وردية مرتبطة بتكليف |
| `GET /api/employees?is_active=true` | قائمة الموظفين، مع مرشح اختياري للحالة النشطة |
| `POST /api/employees/sync` | جلب الموظفين وأسمائهم من SmartPSS وتحديث سجل راصد المحلي؛ للمشرف فقط |
| `POST /api/employees`, `PUT /api/employees/{employee_id}`, `DELETE /api/employees/{employee_id}` | إنشاء موظف وتعديل بياناته أو تعطيله (الحذف منطقي) |
| `GET /api/employee-shifts?employee_id=16` | تكليفات الورديات المؤرخة، اختيارياً لموظف محدد |
| `POST /api/employee-shifts` | إسناد وردية لموظف بتاريخ بداية ونهاية اختياريين؛ يرفض التداخل بـ `409` |
| `GET /api/employee-branches?limit=50&offset=0` | سجل نقل الفروع مع `is_current` و`is_future` وترقيم صفحات |
| `POST /api/employee-branches` | إضافة نقل مؤرخ إلى فرع؛ يرفض تواريخ التداخل بـ `409` |

يمكن إلحاق `employee_id` بمسار الحضور كمعرّف نصي. جسم إنشاء الموظف يحتوي `employee_id` و`employee_name`؛ جسم إسناد الوردية يحتوي `employee_id` و`shift_id` و`start_date` و`end_date` الاختياري. ترجع مسارات الموظفين والتكليفات تواريخها؛ حالة التكليف تُستنتج من تاريخ البداية والنهاية. إسناد الوردية المستقبلي لا يسري قبل تاريخ بدايته.

مثال:

```bash
TOKEN=$(curl -sS -X POST http://127.0.0.1:8000/api/auth/login \
  -H "Content-Type: application/json" \
  -d "{\"username\":\"$RASID_LOGIN_USERNAME\",\"password\":\"$RASID_LOGIN_PASSWORD\"}" | python -c "import json,sys;print(json.load(sys.stdin)['access_token'])")
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/api/attendance/today
```

جسم طلب `POST /api/employee-branches`:

```json
{
  "employee_id": "16",
  "employee_name": "سالم",
  "branch_name": "فرع العليا",
  "start_date": "2026-11-01"
}
```

إنشاء موظف ثم إسناد وردية له (استخدم `shift_id` من `GET /api/shifts`):

```json
{
  "employee_id": "16",
  "employee_name": "سالم",
  "is_active": true
}
```

```json
{
  "employee_id": "16",
  "shift_id": 1,
  "start_date": "2026-11-01"
}
```

جسم الوردية يقبل `lateness_mode` بالقيمة `after_grace` أو `from_start`، و`end_date` في تكليف الموظف اختياري؛ إذا حُذف يبقى التكليف مفتوح النهاية ويُغلق عند إضافة تكليف لاحق.

## منطق الحضور

- **فلترة التبصيم المتكرر (debounce):** بصمتان لنفس الموظف في المدة `DEBOUNCE_MINUTES` (الافتراضي 5 دقائق) تُحتسبان بصمة واحدة (الأولى).
- **سياسة التأخير لكل وردية:** `after_grace` يبدأ احتساب دقائق التأخير بعد فترة السماح؛ `from_start` يحتسبها من بداية الوردية. تأخذ التقارير في الاعتبار التكليف الساري للموظف في تاريخ الوردية.
- **الورديات الليلية:** إذا كان وقت النهاية أسبق من البداية، تقع النهاية في اليوم التالي؛ تساوي وقتي البداية والنهاية غير صالح. تنسب بصمات ما بعد منتصف الليل إلى تاريخ بداية الوردية.
- تعرض اللوحة الموظفين النشطين غير المعيّنين حالياً إلى وردية كـ«غير معيّن». هذه حالة إسناد وردية فقط ولا تعني الغياب؛ غياب سجل البصمة لا يثبت الغياب. تعرض سجلات الفروع `is_current` و`is_future`، وتُفهم الحالة المنتهية من انتهاء الفترة وعدم كونها مستقبلية.
- **التوقيت (`APP_TIMEZONE`، الافتراضي `Asia/Riyadh`):** حساب «اليوم» وحدوده ومنتصف الليل والتأخير كله بتوقيت التطبيق.

### سجل الموظفين وحالات الإسناد

يحفظ راصد بيانات الموظف الأساسية محلياً، بينما تبقى أجهزة SmartPSS مصدراً لسجلات الحضور. يدعم النظام إسناد وردية مؤرخاً لكل موظف وإسناد فرع مؤرخاً؛ يمنع تداخل الفترات، ويحدّث نهاية الإسناد السابق عند إضافة إسناد تالٍ. تظل حالة الموظف النشط مستقلة عن وجود بصمة.

تظهر إسنادات الفرع في API بحالتي `is_current` و`is_future`؛ الإسناد الذي يبدأ لاحقاً مجدول ولا يصبح سارياً قبل تاريخ بدايته. تعرض الواجهة الموظف النشط الذي لا يملك تكليف وردية ساري المفعول ضمن فئة «غير معيّن». لا يجوز تفسير عدم الإسناد أو غياب البصمة بحد ذاته على أنه غياب عن العمل.

### نمط فهم توقيت البصمة (`ATTENDANCE_EPOCH_IS_LOCAL`)

عمود `AttendanceDateTime` يُخزَّن كـ epoch بليغي. المتغيّر يحدد معناه:

- `true` (الافتراضي، **موافق للبيانات الحالية**): الرقم هو **وقت محلي مُرمَّز كـ epoch**. تحقّق في بياناتك: الفرق بين `AttendanceDateTime` و `AttendanceUtcTime` ثابت `+10800` ثانية (3 ساعات) في كل الصفوف تقريباً → الرقم محلي.
- `false`: الرقم **UTC حقيقي**. اختره فقط إذا كان العمود يساوي `AttendanceUtcTime` فعلياً.

تغيير هذه القيمة يؤثر مباشرة على حدود اليوم المعروضة وساعات البصمات.

## الأمان

- **لا ترفع `.env` إلى Git** — مُضاف إلى `.gitignore`. `.env.example` يحوي قوالب فقط.
- قاعدة التطبيق SQLite محلية؛ بياناتها في `backend/data/rasid.sqlite3` أو حجم Docker `rasid-data`. احتفظ بنسخة احتياطية من الملف/الحجم.
- حساب قاعدة SmartPSS يُستخدم للقراءة فقط؛ خزّن بياناته في إعدادات الخادم، ولا تمنحه صلاحيات كتابة.
- دخول المشرف يستخدم رمزاً قصير العمر موقّعاً بسر جلسة؛ لا تسجل كلمات المرور أو رمز Bearer. استخدم TLS عند الوصول عبر الشبكة ودوّر بيانات الدخول/سر الجلسة عند الاشتباه بتسربها.
- إن كان مستودعك يحوي إعدادات قديمة في سجل Git (مثل كلمات سر قديمة) — **غيّرها فعلياً** على الخادم؛ حذف الملف من الـ commit الأخير لا يمحوها من السجل.
- قاعدة البصمة تُقرأ فقط: لا أنشطة كتابة ولا تعديل مخطّط عليها.

## ملاحظات الترحيل

- الجداول القديمة `CHECKINOUT` غير مستخدمة — المصدر الحالي هو `AttendanceRecordInfo`.
- «اليوم» يُحسب بحدود حصرية `[منتصف الليل، منتصف الليل التالي)` بتوقيت التطبيق؛ الوضع القديم كان يحسبها بتوقيت UTC/الحاوية مما يستبعد بصمات الصباح الباكر أو يضيف أمسيات الأمس.
